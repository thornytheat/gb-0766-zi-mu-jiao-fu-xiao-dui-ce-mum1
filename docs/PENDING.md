# 待选原稿与晚到定稿

## 业务约束

送审截止先交无争议字幕；同轨同号存在两版内容不同的原稿时，两版都不能丢，也不能先挑一版签发。
整轨等待会错过送审，先挑一版又可能与别条字幕撞帧。因此：

1. 文件采信保留冲突组的全部候选稿，状态记为 `PENDING`，不再整组隔离。
2. 候选稿照常走时码、切版、冲突与覆盖流水线，其目标帧在证据包中标记为待定，
   冲突定位区分“已确认重叠”与“候选风险”，覆盖对账把候选帧留在待证侧。
3. 证据包新增帧级台账 `frame_ledger`，逐帧给出 `READY` / `PENDING` 判定与来源，
   可直接回答哪些帧可交、哪些待定。
4. 定稿记录通过 `POST /api/delivery/<id>/finalize` 晚到补登：按 (track, cue_id) 选定原行，
   复算并签发新档；同一份定稿（相同决策散列）重试返回同一档号，不重复签发。

## 状态机

```
收样冲突组 ── PENDING（每版候选各占一行，pending=true）
                │
        定稿记录命中某一原行
                ▼
            仅该版 FINAL（pending=false），同组其余候选丢弃
                │
             复算流水线
                ▼
        新档号（输入指纹 + 定稿决策指纹变化）
```

- 定稿决策按 `(track, cue_id, line)` 定位原行，不依赖文本，避免同号异文选错版。
- 定稿指向不存在的组或不属于该组的原行 → `FINALIZE_TARGET`，不产生归档。
- 对已经定稿的组重复提交同一原行 → 幂等返回既有档；换另一版 → 视为新决策，产生新档。

## 帧台账口径

- 整数目标帧来自 KEEP 段，区间左闭右开，端点 `ceil`，与既有交付帧定义一致。
- 帧落在任一待定候选的 KEEP 帧区间内 → `PENDING`；只落在已采信字幕上 → `READY`。
- 候选与他条同占的帧仍计入重叠，但标注为候选风险，不污染已确认重叠数。
- 覆盖守恒：候选源帧不计入交付覆盖，整段留在 `pending`（待证）侧；定稿后转入交付/移除。
